# 项目管理与维护说明书

本手册面向首次维护真实项目的个人开发者，说明一个需求从提出到上线、再到后期维护的完整流程。当前功能入口见[项目README](../README.md)，模块和展示边界见[架构说明](ARCHITECTURE.md)，历史资料字段见[资料维护](../data/README.md)。具体操作记录统一追加到[HISTORY](HISTORY.md)。

## 从哪里开始

| 你现在要做什么 | 入口 |
|---|---|
| 第一次接手项目 | 阅读目标、角色、流程和开发与测试，先运行现有检查 |
| 修正一条历史资料 | 填资料修订卡，按资料维护约定核对来源、日期、ID和引用 |
| 修复界面或增加交互 | 先写需求与验收条件，再确认模块范围、开发、浏览器验收 |
| 发布已通过验收的修改 | 按发布与部署执行，再核验线上资源 |
| 查找旧截图或处理脚本 | 按[归档与清理](#临时文件归档与清理)核对手动保留的副本；已提交文件也可从Git历史恢复 |
| 处理失败、误改或后期问题 | 查看故障与回退、后期维护；在历史中记录已发生的事实 |

## 项目目标与范围

本项目帮助读者在共同年代下对照政权、君主、事件和人物活动，查看传记、纪年异说及史源。十一专题共用静态程序，完整dist可离线打开；个人博客通过链接进入独立的时间线站点。

范围由具体需求卡决定。资料日期、稳定ID、来源、专题作用域和兼容链接按既有规则维护；代码改进与史实判断分别确认。技术校验能发现错误格式或悬空引用，史料结论需要文献核对。

质量要求包括：主要阅读入口可操作，手机和桌面布局清楚，未知日期不编造定位，旧分享与阅读恢复保持约定，发布资源可核对，失败有恢复路径。性能以相同条件下的测量和资源体积判断，单次加载时间不作为所有设备的保证。

## 谁负责什么

| 角色 | 在个人项目中的职责 |
|---|---|
| 需求负责人（你） | 决定服务对象、优先级、范围与取舍，批准需要实施的方案 |
| 实现与检查者 | 分析现有代码，按范围实现、自查并提供测试和差异证据；可由你或AI助手承担 |
| 资料校核者 | 核对版本、卷次、页码/段落、年代换算和异说；未核实内容保持待考 |
| 验收者（你） | 按真实场景检查结果，决定是否解决了原问题、是否发布 |
| 维护者 | 保管源码和必要备份，处理反馈、依赖升级、归档和故障 |

一个人可以承担多个角色，但仍分别回答“做什么”“如何实现”“怎样证明可用”。交给AI或其他协作者时，明确允许改哪些文件、必须保留什么、需要提交哪些证据。

## 项目流程与计划

~~~mermaid
flowchart TD
  A[提出需求与验收条件] --> B[确认范围、优先级和方案]
  B --> C[独立分支开发与自查]
  C --> D[自动测试与浏览器检查]
  D --> E[用户按场景验收]
  E --> F[合并、发布与线上核验]
  F --> G[记录结果与后期维护]
  G -->|新需求或反馈| A
  D -->|未通过| C
  E -->|未满足约定| B
~~~

一次版本围绕一个清楚目标组织。先列任务和完成条件，估算实现、校核、验证及返工的工作量，再选本次范围。需求可使用“待选择→已批准→实现中→待验收→可发布→已交付”状态；没有验证的结果继续保留待验收状态。

优先级可以简单分为：影响资料正确或主要功能的问题、明显影响阅读的问题、可以稍后考虑的改善。问题由现象和影响决定，不以改动文件数量判断重要性。

## 需求与验收条件

“想优化一下”还需要补充具体场景。例如左列排版需求可写为：秦汉和五代在375px手机宽度下，组标题、政权名称与年代分别可见且不互相覆盖；宋辽金默认宋在首行；原历史日期、ID和分享链接保持。

需求卡只需足够让实现者和验收者判断结果：

~~~text
编号/标题：
谁在什么场景遇到问题：
当前现象与复现步骤：
期望结果：
本次范围与保留约束：
验收条件（可观察或可测量）：
优先级与依赖条件：
负责人/当前状态：
~~~

需求可以是一条GitHub Issue或会话中明确的需求卡；同一项持续使用同一编号。没有证据的推测标明“待验证”。方案中发现额外问题时记入候选清单，按优先级另行选择。

## 方案与架构判断

先查是否已有实现，再决定扩展哪个模块。资料修订、构建投影、页面排版、视图状态和导出各有边界，位置见[架构说明](ARCHITECTURE.md#目录与模块)。方案写清影响的文件、需要保持的接口、验证办法及恢复方式。

一般不为单个界面问题同时改动资料模型。资料格式或公共接口确需变化时，单独列兼容方案、旧数据处理和验收条件。可选方案的比较围绕收益、实施范围和维护成本，保持个人项目能理解和维护。

## 开发与测试

### 环境与独立分支

需要Node.js 22或更高版本。常规构建及Node测试无需第三方运行时依赖；真实浏览器检查使用锁定的开发依赖和本机Chrome或Playwright Chromium。

先在项目根目录查看工作状态：

~~~sh
git status --short --branch
~~~

保存已有工作，确认从已同步的master建立独立分支，例如：

~~~sh
git switch -c change/req-001-labels
~~~

分支是隔离本次修改的工作线，不复制另一套手工维护的资料。保留原有未提交工作，不将无关文件混入本次改动。

### 基线、实现与检查

修改前运行已有检查，确认起点正常。修改资料或源码后使用统一入口生成产物：

~~~sh
node build.mjs
node build.mjs --check
node --test tests/*.test.mjs tests/*.test.cjs
~~~

build负责生成完整dist；--check只比对，不写文件。源文件与对应生成物一起提交，dist不直接编辑。传记总集由构建直接校验与补充。

小步实现，每一步检查差异、运行受影响的验证，再保存独立提交。使用git diff确认实际改动，明确选择本次文件后提交，提交信息说明问题和结果。字段、日期或旧接口有固定样本保护时，先查明失败原因，不通过重算预期掩盖回归。

遇到基线失败、范围明显扩大、需要新依赖或必须改变未批准的外部行为时，先说明影响和取舍。实现检查至少关注：是否重复已有逻辑，是否遗漏异常路径，是否修改无关文件，是否留下调试或临时内容，当前文档是否仍与代码一致。

受限环境不能创建测试子进程时可使用node --test --test-isolation=none；Windows父目录realpath的EPERM可为Node命令添加--preserve-symlinks --preserve-symlinks-main。真实浏览器需要先安装开发工具：

~~~sh
npm ci
npx playwright install chromium
~~~

检查脚本优先使用其支持的本机Chrome；可设置PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH指定兼容浏览器。依赖安装和系统依赖准备可能耗时，结合输出与实际步骤判断状态。

### 哪些检查对应哪些问题

| 检查 | 命令 | 主要证明什么 |
|---|---|---|
| 规则与数据回归 | 上述Node测试命令 | 格式、引用、纪年、状态、旧链接、查询和输出约定 |
| 默认浏览器套件 | npm run test:figures | 人物入口、年份编辑、主题、默认/全部政权的左列边界与响应式布局 |
| 完整展示 | node tests/browser-presentation.mjs | 实际时间线、筛选、搜索、阅读恢复、分享、JSON与图片PDF |
| 触控 | node tests/browser-p0.mjs | 惯性、双指缩放、抽屉、键盘与拒绝存储 |
| 语义与无障碍 | node tests/browser-p1.mjs；node tests/lighthouse-p1.mjs | 语义、键盘链及自动审计 |
| 静态呈现与实体导航 | node tests/browser-publication.mjs；node tests/browser-stage4.mjs | 无脚本年表、输出、区间事件与跨卷链接 |
| 线上完整展示 | node tests/browser-presentation.mjs https://chrunge.github.io/Zhou-Dynasty-Timeline/ | 实际HTTPS入口的展示和交互 |
| 发布一致性 | node tests/verify-release.mjs | 线上清单、全部资源散列、HTML版本引用及根入口 |

按改动选择必要检查。排版和交互必须在浏览器检查；史料修订还需人工校核来源。说明文档和归档整理重点检查链接、完整性、恢复方式及原生成物保持。自动检查不能证明所有设备、字体、打印和史实均正确。

测试报告与截图按需生成在.validation中，归档旧内容后测试会重建该目录。旧命令sync-data.mjs、enrich-context.mjs、enrich-people.mjs、tools/build-biography-core.mjs均转调统一构建，不维护平行资料副本。

## 用户验收与交付标准

测试检查技术规则，验收检查是否满足需求。验收者按需求卡重走实际操作，记录设备或宽度、输入、期望、结果与证据；每项标为通过、失败或待确认。

| 场景 | 可采用的验收办法 |
|---|---|
| 界面排版 | 打开目标专题，在手机与桌面检查标题、名称、年代、遮挡和操作目标 |
| 日期和查询 | 核对约定年份，区分承位与元年，跨公元不出现公元0年 |
| 搜索和详情 | 查找指定人物/事件，确认详情身份、来源及返回位置 |
| 阅读与分享 | 保存后重开页面，打开分享链接，确认年份、选择和详情 |
| 导出 | 打开实际生成的JSON/PDF或图片，核对内容、格式和来源 |
| 史料修订 | 对照出处与异说，确认文字与采用口径符合本次约定 |

完成条件包含：本次目标满足、必要测试通过、实际验收有结果、现行文档已同步、没有未说明的高影响问题。发布后还要核验线上版本。只有Node测试通过时，记录应明确人工或浏览器验收尚未完成。

## 发布与部署

线上地址：[历史时间线](https://chrunge.github.io/Zhou-Dynasty-Timeline/)。个人博客使用域名根路径，时间线使用项目子路径，两者独立部署，无需复制源码到博客。

### 工作流

[site.yml](../.github/workflows/site.yml) 使用 Node.js 22，发布分支为 master，上传目录为 dist。

| 阶段 | 行为 |
|---|---|
| 检查 | PR、master 推送和手动运行检查已提交生成物，运行全部 Node 测试并构建 |
| 浏览器 | 安装锁定的开发依赖与 Chromium，运行真实人物入口与分组左列边界回归，覆盖手机、桌面及关键响应式宽度 |
| 可选 PNG | 手动 social_png 开启时安装中文字体、暂存 PNG 并由构建入口发布 |
| 上传 | 检查全部成功后仅上传 dist |
| 部署 | 仅 master 推送或 master 手动运行部署；PR 和其他分支不部署 |

检查作业只有 contents:read；部署作业使用 pages:write、id-token:write 和 github-pages 环境。工作流按引用分组控制并发，不取消正在执行的部署。开发依赖不进入发布目录。

### 仓库设置

仓库 Settings → Pages → Build and deployment → Source 选择 GitHub Actions。账户、组织和 github-pages 环境策略须允许对应部署，环境分支限制与 master 一致。若 github-pages 设置了所需审批人，检查通过后由具备权限的身份批准该次发布；等待审批不表示构建失败。

### 本地准备与发布

按[开发与测试](#开发与测试)验证源码和生成物，将它们一起提交。合并到 master 并推送后，工作流自动执行；检查失败不会部署。运行状态见 [Actions](https://github.com/Chrunge/Zhou-Dynasty-Timeline/actions)，线上产物可与 [release.json](../dist/release.json) 的 releaseId 和资源散列核对。

页面、数据、代码和样式必须作为同一 dist 发布。资源版本参数由构建维护，相同源码生成相同入口；不要手动改 dist 或只复制某个脚本。

### 可选PNG社交图

默认使用 SVG。需要 PNG 时，可在 master 手动运行中开启 social_png；本地流程为：

~~~sh
npm ci
npx playwright install chromium
node build.mjs
node tools/render-social-previews.mjs
node build.mjs --social-png-dir=.validation/social-png
node build.mjs --check --social-png-dir=.validation/social-png
~~~

本机已有 Chrome 时可设置 SOCIAL_CHROMIUM_CHANNEL=chrome，或用 PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH 指定兼容浏览器。渲染离线运行，中文字体影响结果；PNG 不要求跨操作系统字节一致。构建检查 PNG 头部、1200×630尺寸、原 SVG 与 PNG 散列，拒绝陈旧输入。普通检查使用默认 SVG，PNG 模式须携带相同参数。

### 排障

| 现象 | 检查方式 |
|---|---|
| dist 缺失或过期 | 重新构建并提交生成物 |
| 引用校验失败 | 修正稳定 ID、显式专题作用域或有依据的未收录声明 |
| 浏览器验收失败 | 查看具体入口与 .validation/figures/ 报告，不使用强制点击掩盖遮挡 |
| Pages 权限错误 | 检查来源、Actions 权限、组织策略和环境限制 |
| 部署被跳过 | 确认推送或手动运行的分支为 master |

原 Sites 配置 .openai/hosting.json 不参与 Pages 工作流。部署与验收历史见 [HISTORY](HISTORY.md)。


## 故障与回退

先区分构建、环境审批、部署和线上缓存四个阶段：

| 现象 | 下一步 |
|---|---|
| 构建或测试失败 | 查看第一个实际失败项，核对本次差异与基线；恢复自己这一小步的修改后重新确认 |
| 等待环境批准 | 检查github-pages审批人，由有权限的身份放行该次已验证发布 |
| 依赖安装耗时 | 查看步骤是否仍有进展和错误；单凭耗时不能认定程序失败 |
| 运行显示取消 | 查看触发原因、取消操作与工作流并发配置，确认是否需要重试 |
| 部署成功但页面仍旧 | 对比线上release.json、资源版本与散列，再检查浏览器缓存和入口 |
| 上线后确认回归 | 选定已知正常版本，生成可审查的回退提交，经检查重新发布整套资源 |

回退前保留现场与日志，只处理本次相关修改。git log可查看提交；确认目标后用git revert生成回退提交，维护者核对冲突后执行原测试和发布流程。资料回退同样要检查引用、日期及来源。Git能恢复已提交内容，忽略提交的归档包需要本地或其他备份。

## 后期维护与归档

| 时机 | 维护内容 |
|---|---|
| 每次需求开始 | 看清工作区、确定范围、运行起点检查，列出验收条件 |
| 每次资料修订 | 按数据约定检查ID、引用、纪年与出处，保存未核实状态 |
| 每次发布 | 保存提交、Actions链接、releaseId和实际验收结果；检查线上资源 |
| 定期人工检查 | 处理反馈、抽查主阅读路径与来源链接，按需评估锁定依赖升级 |
| 临时内容增多时 | 按[归档与清理](#临时文件归档与清理)打包、校验、恢复或手动清理 |

releaseId是完整发布资源的指纹，用来判断本地与线上是否为同一批文件。维护历史只追加到HISTORY，记录真实已存在的提交，避免给文档填入自己的提交哈希。纯历史证据提交使用[skip ci]时说明原因；代码、资料或发布资源变更仍按完整检查流程处理。

运行生成物有不同用途：dist是交付物，固定测试样本是验证基础，node_modules是可重建的开发环境，.validation是可归档的报告和缓存。归档包由维护者手动保留或清理，实际副本以文件为准；规则见下节。压缩包与逐文件清单仅在本地，Git不替它们提供备份。

## 临时文件归档与清理

arichive/是按需创建的本地归档位置，整目录忽略提交。归档时按浏览器临时配置、验收证据、一次性脚本及工具缓存分类打包，保留来源路径、文件数、原始体积和SHA-256清单。压缩包与逐文件清单由维护者自行备份或清理。

先核对目标路径和占用，再压缩并逐文件校验。校验完整后移走原临时内容，包中保留原相对路径，以便恢复。需要恢复时先校验包，在独立的空审阅目录解压，核对用途后复制所需文件；一次性脚本先检查写入目标和适用资料，再决定是否运行。

| 内容 | 保留或清理建议 |
|---|---|
| 测试浏览器配置、工具缓存 | 可重建，确认所需报告完整后优先手动清理 |
| 截图、日志和上线验收证据 | 可按最近2—3个验收版本或约90天留存，实际由维护需要决定 |
| 一次性人工脚本 | 核对用途后决定，无法判断时保留 |
| 原始资料、唯一历史备份及固定样本 | 单独确认价值，不按普通临时缓存处理 |

删除工作区中的已提交文件后，Git历史仍保留对应版本，可按路径查找并恢复；忽略提交的压缩包和本地清单无法依赖Git恢复。历史中的旧路径表示当时的位置，当前说明以实际工作区和本手册为准。

## 待选择的后续改善

以下是候选需求，实施范围需另行选择：

| 方向 | 待评估内容 | 选择依据 |
|---|---|---|
| 临时产物生命周期 | 测试浏览器配置采用独立临时位置，结束后释放，报告按规则留存 | 减少重复积累；本手册不改变测试程序 |
| 资料质量 | 小批核对待考条目，补充可定位的文献依据；评估未单列事件是否建档 | 先有出处和明确采用口径 |
| 数据传输 | 测量大型专题中兼容投影的重复传输，再决定精简方式 | 有实际体积或初始化瓶颈，且保持旧接口和导出 |
| 博客入口 | 评估十一专题的展示名称与工具介绍页、阅读示例 | 让读者理解范围并开始使用 |
| 发布策略 | 明确博客的新提交取消旧运行与时间线排队策略的用途 | 结合个人更新习惯与验收需要决定 |

这些候选项作为需求来源维护，不自动转为本次开发任务。当前实现与架构以现行代码和架构说明为准，已发生的选择和实施过程以HISTORY为准。
